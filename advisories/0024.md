# Remote code execution in NGINX (nginx2root: CVE-2026-123007, CVE-2026-123633, CVE-2026-123634, CVE-2026-121810, CVE-2026-113425) affects the Mirantis OpenStack for Kubernetes (MOSK) management console

### Release Date

2026-11-24

### Overview

On November 18, 2026, the NGINX project released NGINX 1.31.9 (mainline) and 1.30.7 (stable), fixing five memory-safety vulnerabilities published by Xint under the name **nginx2root**. Each vulnerability is an independent attack path; which one applies depends on the NGINX configuration:

| CVE | Affected configuration | First affected release | NGINX severity |
| --- | --- | --- | --- |
| [CVE-2026-123007](https://www.cve.org/CVERecord?id=CVE-2026-123007) | HTTP/2 enabled | 1.9.5 | Major |
| [CVE-2026-123633](https://www.cve.org/CVERecord?id=CVE-2026-123633) | HTTP/2 enabled and requests forwarded to an upstream (backend) server | 1.19.7 | Medium |
| [CVE-2026-123634](https://www.cve.org/CVERecord?id=CVE-2026-123634) | `resolver`, a request-derived `proxy_pass` destination, and a subrequest such as `mirror` | 0.6.18 | Medium |
| [CVE-2026-121810](https://www.cve.org/CVERecord?id=CVE-2026-121810) | HTTP/3 (QUIC) with requests forwarded to an upstream server | 1.25.0 | Medium |
| [CVE-2026-113425](https://www.cve.org/CVERecord?id=CVE-2026-113425) | Mail proxy using `proxy on` and `auth_http` | 0.5.15 | Major |

The most impactful issue, **CVE-2026-123007**, allows an **unauthenticated** remote attacker to execute commands with the privileges of the NGINX worker process on any server that has HTTP/2 enabled. The researchers also report a separate Linux kernel vulnerability in the SCTP subsystem, not yet assigned a CVE, which they chained with the NGINX vulnerabilities to gain root privileges on the host, including from inside a container.

Every NGINX binary shipped in current MOSK releases is in the affected version range and is built with the HTTP/2, HTTP/3, and mail modules, so the vulnerable code is present in all of them. Whether a component is **exploitable** depends on its configuration. Mirantis analyzed the shipped configuration of every NGINX-based component. One component, the **management console**, is exploitable as shipped.

### Affected Products

Mirantis OpenStack for Kubernetes 26.2 and 26.2.1, MOSK management clusters and MOSK clusters. No released version contains the fix.

#### Legacy NGINX Ingress

Legacy NGINX Ingress is a parallel case: it also contains an affected NGINX build (1.27.1), but it is **not** listed under [NGINX-based components](#nginx-based-components) and **will not be rebuilt** for this advisory. Starting with MOSK 26.2, Envoy Application Gateway (`app-gateway`) is the preferred ingress layer for OpenStack, Ceph, and OpenSDN public endpoints and supersedes legacy NGINX Ingress (`openstack/extra/nginx-ingress-controller`), which was [declared deprecated](https://docs.mirantis.com/mosk/26.2/deprecation-notes/openstack-depr.html#nginx-ingress) and remains available only for a transition period until MOSK 27.1.

Existing MOSK clusters that still use NGINX Ingress need to migrate to Application Gateway as described in [Migrate public endpoints to Envoy Proxy](https://docs.mirantis.com/mosk/26.2/ops/openstack-operations/migrate-app-gateway.html). Until the migration is complete, apply the [workaround](#legacy-openstack-nginx-ingress-turn-off-http2). After the migration, make sure that the legacy ingress pods are removed or no longer reachable, as described in [Clean up the cluster](https://docs.mirantis.com/mosk/26.2/ops/openstack-operations/migrate-app-gateway.html#clean-up-the-cluster).

### Vulnerability Information

**CVE-2026-123007** is an integer underflow in HTTP/2 flow control. A client can push the connection-level send window past its permitted maximum by combining `WINDOW_UPDATE` frames with stream cancellation. A later unsigned subtraction then underflows and produces an invalid memory-copy length, which the researchers used to disclose memory addresses, corrupt the heap, and redirect execution through a cleanup function pointer. Attack traffic consists of HTTP/2 control frames, which are not written to access logs.

**CVE-2026-123633** is a use-after-free. An HTTP/2 connection with an incomplete frame can stay in NGINX's queue of reusable connections. When a request on that connection opens an upstream connection while connection slots are scarce, NGINX can close and free the request it is still processing.

**CVE-2026-123634**, **CVE-2026-121810**, and **CVE-2026-113425** are use-after-free vulnerabilities in the DNS resolver, HTTP/3 stream handling, and mail proxy authentication respectively. None of these features is enabled in the shipped configuration of any component listed above.

### Threat Landscape for MOSK

**Management console — critical.** MOSK management console is the entry point that cloud operators use to manage all MOSK clusters. As shipped, HTTP/2 feature is enabled on both TLS listeners (`listen 8443 ssl http2;`, `listen 8444 ssl http2;`). The service is published by a `LoadBalancer` on ports 443 and 8444, requests are proxied to IAM system (Keycloak) and to management API services, and no client certificate is required. An attacker who can open a TLS connection to port 443 or 8444 of the console address can attempt CVE-2026-123007 and CVE-2026-123633 without authentication.

The NGINX master and worker processes run as the unprivileged user `nobody` (UID 65534), the container drops all Linux capabilities, and it disallows privilege escalation. This does not lower the severity, because everything the console pod can read is readable by `nobody`, and code execution in the NGINX worker can provide the attacker with:

- **Operator access to every managed cluster** The pod's Kubernetes service account token is mounted into the NGINX container. The service account can read Secrets in all namespaces, which includes the operator's kubeconfig of every cluster that the MOSK management cluster manages.
- **A token that does not expire.** The Secret `kaas/kaas-ui-token` holds a legacy service account token for the same service account, which stays valid across pod restarts until the Secret is deleted.
- **User's credentials.** The worker terminates TLS for the console and proxies users' requests to Keycloak and the Kubernetes API, so it sees passwords and the bearer tokens of every console request in plain text.
- **The console's TLS private key,** which must be readable by `nobody` because the NGINX master also runs as `nobody`.
- **Attacker-controlled code in every operator's browser.** The web root is writable by `nobody` and the root file system is not read-only, so an attacker can alter the JavaScript the console serves. Every operator who then opens the console runs that code in their browser until the pod restarts.
- **Outbound reachability from the pod** to the Kubernetes API, Keycloak, other internal services, and whatever networks the management-cluster node can reach.
- **Root access the management node host OS,** through the kernel SCTP vulnerability. Opening an SCTP socket as any user makes the kernel load the SCTP module, and the container runs without a seccomp filter. The container hardening described above does not prevent this escalation.

**Other NGINX-based components — low.** The remaining components contain the vulnerable code but do not enable any of the affected features as shipped. They become exploitable only if their configuration was customized in a particular environment:

- **Artefact cache.** HTTP/1.1 only (`listen 8443 ssl;` without `http2`); no `resolver`, `mirror`, QUIC, or mail configuration.
- **Bare Metal subsystem - Ironic Inspector proxy.** HTTP/1.1 only on TLS ports 5050 and 6385 and plain HTTP port 80; upstream hops use `proxy_http_version 1.1`.
- **StackLight Alerta.** Single plain HTTP listener (`listen 8080`), uWSGI backend; `ClusterIP` service only. The service sits behind `iam-proxy-alerta`, which is not NGINX-based.
- **Ironic conductor HTTP server.** HTTP/2 is not enabled. It is reachable only inside the MOSK cluster and has no authentication, so it must never be exposed externally.

### Detection

The following checks are read-only. Run them against each MOSK management cluster, and against MOSK clusters for StackLight Alerta.

**1. Check whether the management console offers HTTP/2.** First obtain the console address from the `kaas-kaas-ui` service:

```shell
kubectl -n kaas get svc kaas-kaas-ui -o jsonpath='{.status.loadBalancer.ingress[0].ip}{"\n"}'
```

Then, from each network that can reach the management console, replace `<console-address>` with that address and run the following. The command offers both HTTP/2 and HTTP/1.1, because NGINX rejects the TLS handshake when it supports none of the protocols that the client offers:

```shell
for port in 443 8444; do
  echo "== $port"
  openssl s_client -connect <console-address>:$port -alpn h2,http/1.1 </dev/null 2>&1 \
    | grep -E 'ALPN protocol:|No ALPN negotiated|errno'
done
```

| Output | Meaning |
| --- | --- |
| `ALPN protocol: h2` | HTTP/2 is enabled and reachable from this network. CVE-2026-123007 and CVE-2026-123633 are exploitable from here. |
| `ALPN protocol: http/1.1` | HTTP/2 is off. |
| `errno` | The port is not reachable from this network. |

**2. Inventory every running NGINX and its configuration.** Run the following script from a host that can reach the cluster API, with `KUBECONFIG` set to the kubeconfig of the MOSK management cluster or MOSK cluster under check. The script finds running NGINX processes in all pods and reports the version, the build modules, and the configuration directives relevant to the five vulnerabilities. Containers without a shell are not reported. Repeat for each MOSK management cluster, and for each MOSK cluster that runs StackLight Alerta or the Bare Metal (Ironic) service.

```shell
#!/usr/bin/env bash
# nginx-check.sh — usage: KUBECONFIG=<kubeconfig> ./nginx-check.sh [namespace ...]
K=${KUBECTL:-kubectl}
nss=${*:-$($K get ns -o jsonpath='{.items[*].metadata.name}')}
for ns in $nss; do
  $K -n "$ns" get pods --field-selector=status.phase=Running \
    -o go-template='{{range .items}}{{$p:=.metadata.name}}{{range .spec.containers}}{{$p}} {{.name}} {{.image}}{{"\n"}}{{end}}{{end}}' |
  awk '{w=$1; sub(/-[a-z0-9]{8,10}-[a-z0-9]{5}$/,"",w); sub(/-[a-z0-9]{5}$/,"",w); sub(/-[0-9]+$/,"",w); if (!seen[w" "$2" "$3]++) print}' |
  while read -r pod c img; do
    out=$($K -n "$ns" exec "$pod" -c "$c" -- sh -c '
      for p in /proc/[0-9]*; do
        [ "$(cat $p/comm 2>/dev/null)" = nginx ] || continue
        exe=$(readlink $p/exe)
        conf=$(tr "\0" " " < $p/cmdline | grep -oE "\-c [^ ]+" | cut -d" " -f2)
        echo "  build: $($exe -V 2>&1 | grep -oE "nginx/[0-9.]+|--with-(http_v2_module|http_v3_module|mail)[^ ]*" | sort -u | tr "\n" " ")"
        $exe -T -e /dev/null ${conf:+-c $conf} 2>/dev/null | sed "s/#.*//" |
          grep -nE "^[[:space:]]*listen|http2|quic|^[[:space:]]*(mirror|auth_request)[[:space:]]|ssi[[:space:]]+on|^[[:space:]]*resolver[[:space:]]|auth_http|^[[:space:]]*mail[[:space:]]*[{]" |
          grep -v quicktime | head -40 | sed "s/^/  /"
        break
      done' 2>/dev/null)
    [ -n "$out" ] && printf '== %s/%s/%s (%s)\n%s\n' "$ns" "$pod" "$c" "$img" "$out"
  done
done
```

Example output on an affected MOSK management cluster:

```
== kaas/kaas-kaas-ui-68956b87b5-ckpkf/kaas-ui (mirantis.azurecr.io/core/frontend:1.45.16)
  build: --with-http_v2_module --with-http_v3_module --with-mail --with-mail_ssl_module nginx/1.25.3
  24:        listen 8080 default_server;
  30:        listen 8443 ssl http2;
  75:        listen 8444 ssl http2;
  193:resolver 10.233.0.10;
```

Interpret the output for each NGINX as follows:

| Output | Exploitable CVEs |
| --- | --- |
| A `listen` line with `http2`, or `http2 on;` | CVE-2026-123007; also CVE-2026-123633 if the server proxies requests to an upstream |
| A `listen` line with `quic` | CVE-2026-121810 |
| A `mail {` block with `auth_http` | CVE-2026-113425 |
| A `resolver` line together with a subrequest (`mirror`, `auth_request`, or `ssi on`) and a `proxy_pass` destination taken from the request | Potentially CVE-2026-123634; contact Mirantis support with the configuration |
| None of the above | None as configured; the vulnerable code is still present |

**3. Check whether the kernel SCTP module can be loaded on management nodes.** Run on each management node:

```shell
lsmod | grep -w sctp
grep -E '^CONFIG_IP_SCTP=' /boot/config-$(uname -r)
grep -rs sctp /etc/modprobe.d/
```

`CONFIG_IP_SCTP=m` without an `install sctp /bin/false` line in `/etc/modprobe.d/` means that the kernel loads the module on demand, which makes the privilege escalation step available to an attacker.

### Mitigations

There is currently no MOSK release that includes NGINX with the fixes for nginx2root. Mirantis will rebuild the images listed under [NGINX-based components](#nginx-based-components) on fixed NGINX versions and include them in an upcoming patch release. The legacy NGINX Ingress Controller is not rebuilt; migrate away from it as described in [Legacy NGINX Ingress](#legacy-nginx-ingress). Plan to update when the patch release becomes available, and apply the [Workarounds](#workarounds) until then.

Upstream fix status as of 2026-11-18:

| Source | Fixed version | Status |
| --- | --- | --- |
| nginx.org | 1.31.9 (mainline), 1.30.7 (stable) | Released 2026-11-18. These releases also fix other vulnerabilities not covered by this advisory. |
| Alpine Linux | `nginx 1.30.7-r0` | Released for Alpine 3.24 and edge. The affected MOSK images use Alpine-packaged NGINX. |
| NGINX Ingress Controller | — | No fixed release. Will not be rebuilt; see [Legacy NGINX Ingress](#legacy-nginx-ingress). |

### Workarounds

Apply the following workarounds until the patch release with fixed NGINX is installed.

#### Management console: turn off HTTP/2

Turning off HTTP/2 in the management console NGINX blocks CVE-2026-123007 and CVE-2026-123633. With this change, none of the five vulnerabilities can be reached in the shipped management console configuration. The console keeps working over HTTP/1.1; pages may load slightly slower.

The change removes `http2` from the two TLS listeners in the `kaas/kaas-kaas-ui-nginx` ConfigMap: `listen 8443 ssl http2;` becomes `listen 8443 ssl;`, and `listen 8444 ssl http2;` becomes `listen 8444 ssl;`. Perform the following steps on each MOSK management cluster.

**Step 1. Back up the ConfigMap and remove `http2` from both listeners**

```shell
kubectl -n kaas get cm kaas-kaas-ui-nginx -o yaml > kaas-kaas-ui-nginx.backup.yaml
kubectl -n kaas get cm kaas-kaas-ui-nginx -o json \
  | jq '.data["nginx.conf"] |= gsub("ssl http2;"; "ssl;")' \
  | kubectl replace -f -
kubectl -n kaas get cm kaas-kaas-ui-nginx -o jsonpath='{.data.nginx\.conf}' | grep -n 'listen'
```

The output of the last command must not contain `http2`.

**Step 2. Restart the management console pods**

Editing the ConfigMap alone does not change the running pods:

```shell
kubectl -n kaas rollout restart deploy/kaas-kaas-ui
kubectl -n kaas rollout status deploy/kaas-kaas-ui
```

The pods restart one at a time, so the console stays available. If the first new pod does not become ready, restore the backup with `kubectl replace -f kaas-kaas-ui-nginx.backup.yaml` and restart the pods again.

**Step 3. Verify that every console pod runs without HTTP/2**

```shell
for p in $(kubectl -n kaas get pods -l app.kubernetes.io/name=kaas,app.kubernetes.io/instance=kaas-ui -o name); do
  echo "$p: $(kubectl -n kaas exec "$p" -c kaas-ui -- grep -c http2 /etc/nginx/nginx.conf)"
done
```

Every pod must report `0`.

**Step 4. Verify from the client side**

From each network that can reach the console, run the check in [Detection](#detection), step 1. It must report `ALPN protocol: http/1.1` or `errno` for both ports.

#### Persistence

**Repeat Steps 1–4 after every MOSK management-cluster update** until you install the patch release with fixed NGINX. An update of the MOSK management cluster restores the original ConfigMap, and HTTP/2 returns when the console pods restart.

#### Legacy OpenStack NGINX Ingress: turn off HTTP/2

On MOSK clusters that still serve OpenStack public endpoints through the legacy NGINX Ingress Controller, turn off HTTP/2 in the `OpenStackDeployment` object until the migration to Envoy Proxy is complete:

```yaml
spec:
  services:
    ingress:
      ingress:
        values:
          conf:
            ingress:
              use-http2: "false"
```

For example:

```shell
kubectl -n openstack patch osdpl <osdpl-name> --type merge \
  -p '{"spec":{"services":{"ingress":{"ingress":{"values":{"conf":{"ingress":{"use-http2":"false"}}}}}}}}'
```

After the change is applied, verify that no ingress pod enables HTTP/2:

```shell
for p in $(kubectl -n openstack get pods -o name | grep ingress); do
  echo "$p: $(kubectl -n openstack exec "$p" -c ingress -- nginx -T 2>/dev/null | grep -c -w 'http2 on')"
done
```

Every pod must report `0`. Then run the check in [Detection](#detection), step 1, against the OpenStack public endpoint address. Unlike the management console change, this setting is part of the `OpenStackDeployment` object and persists across updates.

#### Other NGINX-based components

The Artefact cache, the Bare Metal subsystem - Ironic Inspector proxy, StackLight Alerta, and the Ironic conductor HTTP server are less exploitable: they contain the vulnerable code, but their shipped configuration does not enable any of the features that the five vulnerabilities require. They do not require changes. Do not enable HTTP/2, HTTP/3, or the mail proxy in these components, and do not expose the Ironic conductor HTTP server outside the MOSK cluster.

#### Additional measures

1. **Restrict network access to the management console.** Allow TCP ports 443 and 8444 of the management console address only from trusted administrative networks, following the [MOSK management firewall configuration](https://docs.mirantis.com/mosk/26.2/security/firewall-conf/container-cloud.html). The vulnerable code remains in the binary, so this restriction protects the console if HTTP/2 is turned back on, for example by a MOSK management-cluster update.
2. **Prevent loading of the SCTP kernel module on management nodes** if your MOSK management cluster does not use SCTP. Add `install sctp /bin/false` to a `.conf` file under `/etc/modprobe.d/`. This only prevents loading through `modprobe`: it does not unload a module that is already loaded and has no effect when SCTP is built into the kernel (`CONFIG_IP_SCTP=y`). Apply this setting on every management node if you need to prevent an attacker who gains code execution inside a container from becoming root on the node: the container hardening of the affected components does not block this escalation. Mirantis does not provide a dedicated `HostOSConfiguration` module for this setting; apply it with the tooling you use to manage node configuration.
3. **Watch for indicators of exploitation attempts.** A failed attempt can crash an NGINX worker process. Investigate unexpected restarts of the console pods and worker crashes reported in the console logs:

   ```shell
   kubectl -n kaas get pods -l app.kubernetes.io/name=kaas,app.kubernetes.io/instance=kaas-ui
   kubectl -n kaas logs deploy/kaas-kaas-ui -c kaas-ui --since=24h | grep -Ei 'worker process.*exited|signal 11'
   ```

   HTTP/2 control frames are not written to access logs, so a clean access log does not prove that no attempt was made.

### If the Management Console Was Exposed

If the management console accepted HTTP/2 connections from untrusted networks, assume that the console's service account token and the admin credentials of the managed clusters were obtained by an attacker:

1. Close the exposure: restrict network access to the console and turn off HTTP/2 as described in [Workarounds](#workarounds).
2. Look for signs of an attempt, as described in [Additional measures](#additional-measures). If Kubernetes API audit logging is enabled, review which Secrets `system:serviceaccount:kaas:kaas-ui` read. Reads of `<cluster>-kubeconfig` Secrets are expected; reads of other Secrets are not. Also review what the cluster admin credentials were used for.
3. Restart the console pods to invalidate the service account tokens mounted in the old pods and discard any changes to the web root:

   ```shell
   kubectl -n kaas rollout restart deploy/kaas-kaas-ui
   ```

4. Delete the legacy token Secret, which invalidates its token. It is recreated with a new token on the next update:

   ```shell
   kubectl -n kaas delete secret kaas-ui-token
   ```

5. Treat the following as compromised and replace them:
   - the admin credentials in every `<cluster>-kubeconfig` Secret. Replacing these credentials requires rotation of both the MKE client root CA and the MKE cluster root CA of every affected MOSK cluster. Contact Mirantis support for assistance with the rotation;
   - the Keycloak passwords and sessions of everyone who signed in through the console while it was exposed;
   - the management console TLS certificate and key.
6. If the SCTP module could be loaded on a node that ran an exposed console pod, treat that node as compromised.
