# Remote code execution in Java runtimes (OpenJDK Base64 decoder, CVE-2026-114938 "Java4Shell") affects Mirantis OpenStack for Kubernetes (MOSK)

### Release Date

2026-11-19

### Overview

On November 17, 2026, the OpenJDK Vulnerability Group and Oracle published fixes for **[CVE-2026-114938](https://nvd.nist.gov/vuln/detail/CVE-2026-114938)**, publicly named "Java4Shell". It is a heap out-of-bounds write in the HotSpot JVM's hardware-accelerated Base64 decoder. An attacker who can make a Java application decode a crafted, malformed Base64 string can corrupt the JVM heap. The researchers (Calif) demonstrated heap memory disclosure and **remote code execution**, including **pre-authentication** code execution in default Keycloak configurations, and post-authentication code execution in Apache Kafka brokers and Elasticsearch.

The vulnerable code exists only in the x86-64 AVX-512 Base64 decode intrinsic. It runs only when **all** of the following are true:

1. The JVM is OpenJDK-based (any vendor) version **17.0.6 or later**, or any **21, 25 or 27** release without the vendor fix. Standard OpenJDK 8 and 11, and 17.0.0–17.0.5, do not contain the vulnerable code.
2. The CPU visible to the JVM supports **AVX-512 VBMI** (Intel Xeon Ice Lake, Sapphire Rapids, Emerald Rapids, Granite Rapids; AMD EPYC Zen 4 and later). ARM64 hosts are not affected.
3. The JIT has compiled the Base64 decoder (it runs often), and attacker-controlled input reaches `java.util.Base64` basic or URL decoding.

Because condition 2 depends on the node CPU, the same container image can be vulnerable on one node and not on another. Virtual machine nodes are affected when the hypervisor exposes AVX-512 VBMI to the guest (for example, CPU host-passthrough).

### Affected Products

Every MOSK management cluster and MOSK cluster that runs an affected Java runtime on nodes with AVX-512 VBMI is affected until it is updated to a release that contains the fix.

Components confirmed by Mirantis to ship an affected runtime:

| Cluster | Component | Namespace / pod | Java runtime observed |
| --- | --- | --- | --- |
| MOSK management cluster | Keycloak (IAM) | `kaas` / `iam-keycloak` | Red Hat build of OpenJDK `21.0.12+8` |
| MOSK management cluster and MOSK clusters | StackLight OpenSearch | `stacklight` / `opensearch-master` | Eclipse Temurin `25.0.3+9` |
| MOSK clusters with OpenSDN | OpenSDN ZooKeeper | `tf` / `tf-zookeeper` | Eclipse Temurin `17.0.20+8` |
| MOSK clusters with OpenSDN | OpenSDN Cassandra configuration builder | `tf` / `tf-cassandra-config-dc1-rack1` (config-builder container) | Red Hat build of OpenJDK `21.0.12.1+1` |

All MOSK management-cluster and MOSK releases are affected; no released version contains the fix. The runtime versions above were observed on management-cluster release `kaas-2-32-1` (cluster release `k0s-22-0-1-1-33-13`); other releases ship different versions of the same components and are equally affected.

Components verified as **not affected**:

| Cluster | Component | Java runtime | Reason |
| --- | --- | --- | --- |
| MOSK clusters with OpenSDN | OpenSDN Cassandra (`tungsten/cassandra:4.1.11`) | Eclipse Temurin `11.0.31` | Java 11 does not contain the vulnerable code |
| MOSK clusters with OpenSDN | All other OpenSDN images in MOSK 26.2 (operators, 24.1 and 25.1 controller, vRouter, Redis, RabbitMQ, tools) | None | No Java runtime in the image |

The OpenSDN images were checked against the MOSK 26.2 release artifacts by inspecting each image's filesystem.

OpenStack services in MOSK are Python and are not affected. Other Mirantis product lines were not evaluated for this advisory.

### Vulnerability Information

The x86-64 AVX-512 Base64 decode intrinsic miscalculates the store mask for the padded tail of the input. A malformed string ending in `=` (or `==`) causes the decoder to write 62 or 63 bytes past the end of the output array before Java rejects the input as invalid. On Java 21, 25 and 27 the trigger can be as short as 65 characters; on Java 17 it is 129 characters or more. The upstream fix is tracked as JDK-8393212.

### Threat Landscape for MOSK

**Keycloak on the MOSK management cluster — critical.** Keycloak authenticates users of the management Web UI and Kubernetes APIs, which the MOSK firewall documentation permits external clients to reach on TCP 443. The Keycloak network policy shipped in the `iam` chart allows ingress from any address (`0.0.0.0/0`), so network exposure is determined by the perimeter firewall. Calif demonstrated pre-authentication code execution in default Keycloak configurations. Code execution in Keycloak exposes identity and access management for the management cluster and every MOSK cluster it manages, including the ability to issue tokens.

**StackLight OpenSearch — operator-facing only.** OpenSearch runs on the MOSK management cluster and on MOSK clusters. Its HTTP API is reachable only inside the cluster. External access is through OpenSearch Dashboards, which the [StackLight authentication flow](https://docs.mirantis.com/mosk/26.2/ref-arch/stacklight/authentication-flow.html) places behind IAM proxy: the public LoadBalancer hits Keycloak first, and only authenticated operators reach the Dashboards upstream. Exploitation is therefore expected to require authenticated access, consistent with Calif's Elasticsearch result. Code execution would expose collected logs and the StackLight namespace.

**OpenSDN ZooKeeper — operator-facing only.** ZooKeeper is reachable on trusted OpenSDN control-plane networks only. The researchers did not test ZooKeeper, so whether attacker-controlled Base64 input reaches the vulnerable decoder is not established. Code execution would affect coordination of the OpenSDN configuration plane.

**OpenSDN Cassandra configuration builder — not network-exposed.** The configuration builder runs as a container in the `tf-cassandra-config-dc1-rack1` pods and generates Cassandra configuration. It does not serve network requests, so there is no remote attack path to the vulnerable Base64 decoder in this component.

### Mitigations

There is currently no MOSK management-cluster or MOSK release that includes the fix for CVE-2026-114938. Mirantis will rebuild the affected images (Keycloak, StackLight OpenSearch, OpenSDN ZooKeeper, and the OpenSDN Cassandra configuration builder) on fixed Java runtimes as soon as possible.

The rebuild depends on upstream fixes for the Java runtimes these images use (see the table below). Plan to update when a release with the rebuilt images becomes available, and apply the Keycloak workaround in [Workarounds](#workarounds) until then.

Upstream fix status as of 2026-11-18:

| Runtime | Used by | Status |
| --- | --- | --- |
| Red Hat build of OpenJDK | Keycloak, OpenSDN Cassandra configuration builder | **Fix not released.** Red Hat bulletin RHSB-2026-018 rates the flaw Critical; fixes are being expedited. |
| Eclipse Temurin | StackLight OpenSearch (Java 25), OpenSDN ZooKeeper (Java 17) | **Fix not released.** Adoptium publishes builds for OpenJDK security releases; `25.0.5.1` is scheduled for November 2026. |

### Workarounds

The vulnerable code path can be removed by starting the JVM with `-XX:-UseBASE64Intrinsics` parameter. **Apply this workaround only to Keycloak** on the MOSK management cluster. Keycloak is the component most exposed to the outside world, and Calif demonstrated pre-authentication code execution against it.

Do not apply `-XX:-UseBASE64Intrinsics` to StackLight OpenSearch, OpenSDN ZooKeeper, or the OpenSDN Cassandra configuration builder. These components are operator-facing only, and current releases do not provide a sustainable way to pass additional JVM options through the LCM configuration layers. Manually editing their workloads is not durable: controllers can revert the change at any time, which would silently restore the vulnerable configuration, or the edit can overwrite required settings such as the OpenSearch heap size.

#### Keycloak: disable Base64 intrinsics

Disabling the intrinsic switches Base64 decoding to the standard Java implementation. Functional behavior is unchanged; Base64 decoding is slightly slower, which is not expected to be noticeable for authentication workloads. Applying the change triggers a rolling restart of the Keycloak pods, so plan it in a maintenance window.

Apply the mitigation even if the current node has no AVX-512 VBMI, because Keycloak pods can be rescheduled onto newer hardware.

Run these steps from a workstation with `kubectl` access to the MOSK management cluster. Repeat the checks for every Keycloak replica (`iam-keycloak-0`, `iam-keycloak-1`, …); the examples use `iam-keycloak-1`. Keep any existing options in `JAVA_OPTS_APPEND`, including `-Dcom.redhat.fips=false` and `-Djgroups.dns.query=...`; overwriting those options breaks Keycloak clustering or FIPS-related settings.

**Step 1. Check the current flag value**

```shell
kubectl exec -n kaas iam-keycloak-1 -c keycloak -- \
  jcmd io.quarkus.bootstrap.runner.QuarkusEntryPoint VM.flags -all | grep -F UseBASE64Intrinsics
```

A result of `bool UseBASE64Intrinsics = true` means the deployment is not mitigated. Continue with Step 2.

**Step 2. Add the JVM flag to the StatefulSet**

```shell
kubectl edit sts -n kaas iam-keycloak
```

In the `keycloak` container, append `-XX:-UseBASE64Intrinsics` to the `JAVA_OPTS_APPEND` environment variable. Keep any existing options in that value. The result should look like this:

```yaml
spec:
  template:
    spec:
      containers:
      - name: keycloak
        env:
        - name: JAVA_OPTS_APPEND
          value: -Dcom.redhat.fips=false -Djgroups.dns.query=iam-keycloak-headless.kaas.svc.cluster.local -XX:-UseBASE64Intrinsics
```

Save and exit the editor. Kubernetes starts a rolling restart of the pods.

**Step 3. Confirm the pods restarted**

```shell
kubectl rollout status sts/iam-keycloak -n kaas
kubectl get pods -n kaas | grep iam-keycloak
```

The rollout must report completion, and every `iam-keycloak-*` pod must be Running, fully ready, with a recent AGE.

**Step 4. Verify the mitigation is active**

```shell
kubectl exec -n kaas iam-keycloak-1 -c keycloak -- \
  jcmd io.quarkus.bootstrap.runner.QuarkusEntryPoint VM.flags -all | grep -F UseBASE64Intrinsics
```

Expected result:

```
bool UseBASE64Intrinsics                      = false
```

The mitigation is complete when every replica returns `false`.

#### Persistence and rollback

There is currently no supported IAM or LCM configuration that persists `-XX:-UseBASE64Intrinsics` across controller reconciliation. A manual edit of the StatefulSet can be overwritten when the Keycloak release is upgraded or when the IAM chart/controller reconciles the workload. Until a vendor-patched OpenJDK is confirmed in the Keycloak image:

1. After any MOSK management-cluster upgrade, repeat Step 1 and reapply Step 2 if the flag reads `true`.
2. After any unexpected `iam-keycloak` pod restart or IAM Helm/controller reconciliation, repeat Step 1 and reapply Step 2 if the flag reads `true`.
3. Periodically re-run Step 1 on every replica until the patched image is in place.

Remove the flag only after a vendor-patched OpenJDK is confirmed in the Keycloak image.

To roll back, run `kubectl edit sts -n kaas iam-keycloak`, delete `-XX:-UseBASE64Intrinsics` from `JAVA_OPTS_APPEND`, save, and confirm the rollout as in Step 3.

Until those rebuilt images are available and applied, also restrict network access to Keycloak and the management Web UI (TCP 443 on the management cluster's Keycloak and UI addresses) to trusted administrative networks at the perimeter firewall, following the [MOSK firewall configuration](https://docs.mirantis.com/mosk/26.2/security/firewall-conf.html). This remains important because Keycloak is exploitable without authentication. Watch for indicators of exploitation attempts: a failed attempt corrupts the JVM heap and is likely to crash the JVM. Investigate unexpected restarts of `iam-keycloak` pods and JVM fatal error logs (`hs_err_pid*.log`).
