# Host denial of service, with possible remote code execution (Linux kernel IPv4 TCP, CVE-2026-98432) affects Mirantis OpenStack for Kubernetes (MOSK) cluster nodes

### Release Date

2026-11-04

### Overview

On October 15, 2026, the Linux kernel CVE team published **[CVE-2026-98432](https://nvd.nist.gov/vuln/detail/CVE-2026-98432)**, a critical use-after-free vulnerability in IPv4 TCP connection handling. A remote, unauthenticated attacker who can reach an open IPv4 TCP port can trigger a narrow timing race and corrupt kernel memory. The more likely result is a **host kernel crash (denial of service)**. **Remote code execution as root is possible**, but it has not been demonstrated and would require a further exploit chain that controls the freed memory.

The flaw has been present since Linux kernel 4.4. It occurs when the kernel frees IPv4 options associated with a TCP connection request while another CPU may still read those options while processing a retransmitted SYN or a request-socket migration. The primary upstream path affects IPv4; IPv6 is not affected by that path.

Public research describes remote root code execution against a server with a Multipath TCP (MPTCP) listener. CVE-2026-98432 is not specific to MPTCP: disabling MPTCP does not correct the underlying use-after-free. No public proof-of-concept is known to Mirantis. Packets that carry IP options are often dropped before they reach the host, which reduces exposure from outside the operator's network.

### Affected Products

**All MOSK host nodes are affected until their running kernel contains the upstream fix.** The [MOSK compatibility matrix](https://docs.mirantis.com/mosk/26.2/compat-matrix.html) documents host kernels in the **6.8.x** line on current releases (Ubuntu 24.04) and **5.15.x** on older releases (Ubuntu 22.04). This includes management-cluster nodes and MOSK cluster nodes, regardless of role: control plane, compute, gateway, storage, and worker nodes.

The vulnerability is in the host Linux kernel, not in OpenStack or MOSK application code. A node running a custom kernel is affected when that kernel is in one of these lines and does not contain the fix.

Tenant guest kernels are not directly affected by this MOSK host-kernel advisory. A successful compromise of a compute-node host kernel, however, defeats the isolation that protects tenant guests.

Other Mirantis product lines were not evaluated for this advisory.

### Vulnerability Information

CVE-2026-98432 is a use-after-free in the Linux kernel IPv4 TCP stack. During connection processing, `tcp_v4_syn_recv_sock()` can transfer an `ireq_opt` IPv4-options object to a child socket. A concurrent retransmitted SYN may still use that object to construct a SYN-ACK after the child socket has freed it. A related request-socket-migration path can likewise free shared options while another CPU still reads them.

Neither the CVE record nor NVD assigns a CWE. Mirantis classifies the flaw as [CWE-416](https://cwe.mitre.org/data/definitions/416.html) (Use After Free); Red Hat classifies it as [CWE-825](https://cwe.mitre.org/data/definitions/825.html) (Expired Pointer Dereference).

### Threat Landscape for MOSK

The attacker needs no account or user interaction, but must be able to send crafted IPv4 TCP traffic to a TCP listener whose traffic is processed by a vulnerable MOSK node kernel. The public research uses MPTCP, but MPTCP is not a prerequisite of the vulnerability. A trigger that lands is more likely to crash the node kernel. If a further exploit chain achieved code execution, the attacker would have host root.

**Public OpenStack services — primary external exposure.** MOSK exposes OpenStack APIs through MetalLB on the Kubernetes external network. MOSK 26.2 uses the Application Gateway on TCP 443; earlier releases use Ingress on TCP 80 and TCP 443. These endpoints include services such as Keystone, Horizon, Nova, Neutron, Glance, Cinder, Barbican, Heat, Octavia, Placement, metadata, and noVNC. Their traffic is processed by the node kernel before being forwarded to the workload. Nodes advertising these service IPs through MetalLB are therefore the primary externally reachable surface when the external network is accessible to untrusted clients.

**Management services — high-impact access path.** The MOSK firewall documentation permits external clients to access management Web UI and Kubernetes APIs on TCP 443 and 6443, and SSH on TCP 22. If an operator exposes these beyond a restricted administrative network, they are direct remote attack surfaces. Host root on a management node can affect provisioning, identity and access management, artifact delivery, observability, and lifecycle management for its managed MOSK clusters.

**Trusted-network and east-west exposure.** MOSK nodes also provide host-facing TCP services to trusted networks, including Kubernetes and MKE services, kubelet, StackLight exporters, live-migration SSH/libvirt, and VNC. MOSK documentation directs operators never to expose Calico and MetalLB internal ports at a perimeter firewall. Nevertheless, an attacker who has access to an LCM, pod, live-migration, management, or other trusted routed network may be able to reach TCP listeners allowed by that deployment's firewall and service placement.

**Tenant-originated exposure is configuration-dependent.** Tenant networks are normally isolated from MOSK management and cluster-internal networks by the selected Neutron, OVN, Open vSwitch, or OpenSDN backend. A tenant VM does not automatically have a route to host listeners. A tenant that can reach a public service address, provider network, or incorrectly segmented host listener could send the remote traffic, but this is not a demonstrated VM-to-host exploit path.

**Potential Impact (the "Risk").** On a compute node, host root breaks VM tenant isolation. An attacker can inspect guest memory, access or modify tenant virtual disks, and observe or alter host-side virtual network traffic. On management, control-plane, gateway, or storage nodes, host root can expose cluster credentials and control-plane, networking, or storage infrastructure.

### Mitigations

There is currently no MOSK release that includes a Linux kernel with the fix for CVE-2026-98432. Mirantis is waiting for Ubuntu to publish the kernel through its normal delivery process. For current MOSK releases using kernel 6.8.x, Mirantis will include it in an upcoming MOSK patch or major release. Plan a rolling node update and reboot when the release becomes available.

Operators that require a Linux kernel with the fix ahead of a MOSK release can install and pin that kernel themselves. Check [https://ubuntu.com/security/CVE-2026-98432](https://ubuntu.com/security/CVE-2026-98432) to find the version of the kernel with the fix for an Ubuntu kernel from the **same version line** as the currently installed kernel.

Mirantis does not recommend installing kernels from the Ubuntu `-proposed` pocket. Those builds are still in qualification. Wait until Ubuntu publishes the kernel with the fix in the normal `-updates` pocket for the node's release, then install the published package.

Use the MOSK's standard [package host OS configuration module](https://github.com/Mirantis/mosk-host-os-modules/tree/main/package) to add the upstream repository and to install and pin the kernel package. MOSK nodes install packages only from the repositories already configured on the host, and those repositories may lag the Ubuntu `-updates` pocket. Add the matching pocket in the same `HostOSConfiguration`, then install and pin the kernel image together with its modules packages.

| Ubuntu release | MOSK kernel line | Repository suite |
| --- | --- | --- |
| 24.04 (`noble`) | 6.8 | `noble-updates` |
| 22.04 (`jammy`) | 5.15, or 6.8 HWE | `jammy-updates` |

Kernel packages are in the `main` component and are signed by the Ubuntu archive key already present on MOSK nodes, so `repositories[*].key` is not required for `archive.ubuntu.com`. On an air-gapped cluster, mirror the `-updates` pocket to an internal repository and set `repo` to the mirror URL. If the mirror uses its own signing key, set `repositories[*].key` to that key URL. Nodes must be able to reach the repository, including through the cluster proxy when one is configured.

The example below is for Ubuntu 24.04. For another release, change `os_version`, the suite in `repo`, and the package names and versions. Apply a separate configuration per Ubuntu release. Use a `machineSelector` that covers the affected management and MOSK cluster nodes, and roll the nodes through maintenance.

```yaml
apiVersion: kaas.mirantis.com/v1alpha1
kind: HostOSConfiguration
metadata:
  name: cve-2026-98432-kernel
  namespace: default
spec:
  configs:
  - module: package
    moduleVersion: 1.4.0
    values:
      os_version: "24.04"
      repositories:
      - filename: ubuntu-noble-updates
        repo: deb http://archive.ubuntu.com/ubuntu noble-updates main
        state: present
      packages:
      - name: linux-image-<6.8-abi>-generic
        state: present
        version: <package-version>
        allow_downgrade: yes
      - name: linux-modules-<6.8-abi>-generic
        state: present
        version: <package-version>
        allow_downgrade: yes
      - name: linux-modules-extra-<6.8-abi>-generic
        state: present
        version: <package-version>
        allow_downgrade: yes
  machineSelector:
    matchLabels:
      your-custom-label: "true"
```

The module writes the repository to `/etc/apt/sources.list.d/ubuntu-noble-updates.list` and pins the listed package versions. The pin covers only those packages. After the official MOSK release is available, remove the added repository by setting its `state` to `absent` so later host updates continue to come from the MOSK-supported repositories.

Reboot each node and verify the running version with `uname -r`.

Mirantis does not guarantee complete interoperability of MOSK components with custom or third-party kernel packages. The risk of using a later minor package in the same kernel major line — for example, a later 6.8.0 package on a 6.8 host — is considered low. This caveat applies whether the node is on a current supported MOSK release, an older release, or a pre-existing custom-kernel deployment.

### Workarounds

Public guidance describes mitigations that may reduce exposure, including firewall rules that drop IPv4 TCP packets carrying IP options and sysctl configuration that disables MPTCP and/or TCP request migration.

Mirantis has **not** validated that these measures fix CVE-2026-98432 or that they are compatible with MOSK. Operators applying them do so at their own risk. In particular, Ubuntu states that disabling MPTCP is not a complete mitigation because the vulnerability is not MPTCP-specific. Kernel update remains the only permanent resolution.
